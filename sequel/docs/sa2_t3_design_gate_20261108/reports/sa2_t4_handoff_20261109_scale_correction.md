## 3. 実装状態と失敗の具体的原因
- 撮影検証コード: `sequel/tests/sa2_t4_gamehall_relayout_capture.gd`。**既存シーン/コードを改変せず実Godotシーンを起動してからT4画像を追加している。リリース実装ではない。**
- 旧 `stall_game` と宿屋 `n3_brothel` はテスト上で非表示にしている。手前の遮蔽柱1本もx=12.0で非表示。D2カメラ・路地・既存道路・移動帯は据え置き。
- `_add_gamehall()` では現在、QuadMesh作成に相当する
  `game.call("_bt_quad", hall, "gamehall_user_rgba", HALL_X0, 0.0, HALL_X0 + INSERT_W, HALL_H, -6.18, 0.84)`
  で**キャンバス全体**を world 幅7.00m・高4.17mに割り当てる。
- そのため**上部162pxの透明余白も4.17mに含まれてしまい、実物が小さくなる**。
- 外接矩形とマッピングからの算術値（**再実測すること**）:
  - 可視幅 `(1490−47)/1536 × 7.00 = 約6.58m`（設計7.00m未達）。
  - 可視高さ `(1024−162)/1024 × 4.17 = 約3.51m`（設計4.17m未達）。
  - 完成絵の輪郭縦横比 `1443/862 ≈1.674`、物理仕様 `7/4.17≈1.679` なので、**正確な外接矩形トリム→7.00×4.17m割当が第一候補**。歪みは小さいと見込むが実測が必要。
- D2カメラのZ位置による投影縮尺差は物理寸法の不足とは**別問題**。奥行きに依存する見えの調整を先に行って、2D貼付物理寸法のミスを隠さない。
- 前回のログ `T4_PAINTED_ROOF_TOP projected_y=53.41px` は**透明余白を残した状態**の上端の見え方。トリム後の4.17m上端が同じ位置に見える証拠ではない。屋根が切れるかは**トリム後の実画面で再判定**。D2のFOVを勝手に変更しない。

## 4. 次担当の実行手順（確認質問なしで着手）
1. 利用可能なGitHub・実行・表示ツールを調べ、`game-art-animation/tool-routing`、`quality-gate`、`asset-qa`、`create-game-assets`および実行に必要な補助資料を**実際に全文読む**。元正本第8節、現行T4の上記スクリプトとGodot撮影ワークフローも読む。
2. T4ブランチで**まず原画の不透明外接矩形を決定的に再計測**。内部の描き込みに触らず、余白だけをトリムした透過PNGを別の正規ファイルとして出力。元JPEGと現行PNGは保全。元サイズ/アルファbbox/SHA/トリム後のサイズをJSONに記録し、縦横比を検査。
3. テスト専用GodotシーンのQuadMeshを**見えている建物外接矩形が7.00m×4.17m**になるように変更。床接地Y=0、世界X=7.00..14.00m、実物の向き/中心/人物相対縮尺を確定。必要なら画像のトリム後pixel / mをJSONに追記。
4. 撮影前に検査を実装（完成絵の幅・高さが狙いの物理寸法になっていること、元原画との色/画素がトリム部分を除いて維持されていること、外側に不必要な半透明haloがないこと）。GitHub Actionsに寸法チェックを追加して**数値違いでFAIL**させる。現在のCIはファイル存在や描画成功しか検出できない。
5. D2固定で**Godot 4.7.2実画面**のカジノ正面・隣のキャバレー寄り・門寄りを撮影。屋根見切れ・キャラ身長1.85m・視覚縮尺・入口・被写体遮蔽を検証。屋根が見切れたらD2を維持したまま**建物奥行き等の配置の変更でのみ検証**し、干渉・接地とのトレードオフを示す。任意の縮小をしない。
6. **画像はチャット内に直接開く**（PNGを実ファイルとして取得し表示）。ファイルURLのみの返答は不可。動画を制作/撮影した場合も同様。根拠のないPASSをつけない。
7. 完了した変更はT4ブランチのみへ反映・読戻し、Actionsログと画像を確認。main/T2/T3との差分を確認。必要ならこの引き継ぎ正本を結果で更新。
