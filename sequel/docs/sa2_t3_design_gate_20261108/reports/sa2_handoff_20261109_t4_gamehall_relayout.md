## 8. 再発防止：ガイド制作・受け渡し・画像生成・検証の実作業ルール（2026-11-09追記）

**この節は新チャットの必須手順。** 前チャットでは「完成絵が欲しい」のに背景画を生成する、ガイドを作るべき場面で絵を生成する、原本を実際に添付していないのに「貼った」と報告する、存在しているGitHub原本を参考画像へ置き換える、などを反復した。この節を読まずに画像生成しない。

### 8.1 納品物の種類を混同しない
- **形状ガイド**：最初にPython/Pillow等の決定的な描画で作るフラットカラーの正面投影。各色の意味を明示し、物理スケール・描画キャンバス・配置基準（x,y,z、床の高さ）を対応付ける。背景は単色 `#FF00FF`。**油彩塗り・装飾を入れず、設計図的に見える色面だけ**。完成画像や説明図・比較ボードをこれと称してはいけない。
- **完成用塗装画像**：採用された形状ガイドを画像編集入力にして、既存の合格画風に合わせて細密な油彩で塗る。形状、外接境界、透過用の余白を維持する。生成の結果がガイドから逸脱したら不採用。
- **Godot実画面**：Godot 4.7.2内へ正しいスケールで配置して、ゲームカメラで実際に撮影したPNG/動画。画像生成で作るゲーム画面モックやPythonで描いた縮尺線入り画像は**Godot実画面とは呼ばない**。

### 8.2 ガイドの寸法を最初にゲームのコードと整合させる
1. 先に`sequel/scripts/backtown_block.gd`, `sequel/scripts/main.gd`, `sequel/specs/camera_depth.md`, `sequel/art/guide_bt/guide.json`の現行値を確認する。D2カメラ固定、地上約0–4mの可視帯、人物身長1.85mを目安に物理スケールを定義。**これは過去の仕様値であり、今回のGodot実測ではない**。
2. 物理範囲と画像の対応（例：7.5m×5mなら1536×1024、204.8px/m）、各パーツの世界座標、描画順序、後処理用マスク、元画像のSHAを`guide.json`またはガイド専用JSONで固定。正面投影の外観と、入口から見える奥行き部分は区別して設計する。人物や歩行用の地面をガイドに焼き込むかどうかは、パーツ分離仕様に従う（今回の遊技場は人物を別レイヤーにするのが検証対象）。
3. 元の`stall_game.png`は**旧2.4m屋台の原本**。今後の豪華な常設遊技場の制作ガイドとしては**不採用**。以前の「元ガイドを1pxも変えない」は旧屋台用の条件であり、今回の建物再設計へ誤適用しない。
4. 前チャットでPython/Pillowから`sa2_t4_gamehall_low_guide_1536x1024.png`（1536×1024、7.5m幅×5m高の色面ガイド）を作った。**仮案であり、Godot実配置・隣接建物との整合は未検証、最終承認ガイドではない**。生成済みの豪華カジノ画像があるからといって、この仮案が寸法検証に合格したことにはならない。
5. 新配置の案を**実Godotに仮配置してスクリーンショットで判断**する。配置の見直しが終わる前に、ガイドを完成承認・原本固定扱いしない。

### 8.3 GitHubからガイドをチャットへ「実画像で」渡す方法
過去の失敗：GitHub MCPで`fetch_file(...,encoding="base64")`によりPNGの実バイトが取得できても、結果をツール表示しただけでは**ユーザーのチャット画像添付にならない**。Markdownに`![...](relative.png)`と書いたからといって、ChatGPTのImageGenへ自動的に画像編集入力として接続されるわけでもない。`AsyncImage query`やAI生成した「参考画像」を代わりに表示することは禁止。

採用した暫定配布経路：
1. 原本PNGと必要な画風見本・世界観見本をGitHubのT4ブランチに**実バイナリとして**登録（画像ファイルの存在/SHA/解像度を確認）。PNGをアップロードできない場合は「画像の登録未達」と報告。
2. GitHub Markdownの発注書にそれぞれの**実PNGのcommit固定 raw URL**で画像を直接埋め込み、原寸画像を開くリンクも付ける（参考：[旧屋台用画像付き発注書](../../../../art/guide_bt/stall_game_order_20261109.md)；**内容は旧屋台で失効、画像配布方法のみ参照**）。相対画像パスだけのMarkdownではGitHub上の表示状態が受け手の環境次第になるため、絶対URLを優先する。
3. **画像をユーザーがGitHubのページで開き、右クリック「画像をコピー」またはPNGを保存してチャットに画像として貼り付ける。** その添付後、ImageGenには「添付1＝新遊技場ガイド（形状固定）、添付2＝既採用塗装見本、添付3＝`concept_low_dark_a.png`」と割り当てる。これが当チャットで実際にユーザーが旧ガイドを貼り付けられた経路。
4. `raw.githubusercontent.com`リンクは、GitHubのcommitで固定し、画像内容の取り違えを防ぐ。ファイル名やURLだけの提示は「モデルに画像を渡した」証拠ではない。**ユーザーが画像を実添付したことを確認するまで画像編集を始めない**。
5. GitHubからローカル環境への直ダウンロードは前チャットで接続失敗。GitHub MCPはbase64取得に成功したが、その画像をImageGenへ編集入力として自動的に渡すことは検証失敗。Falの画像アップロードは接続先アカウントのクレジット不足（HTTP403）で停止。**再接続・課金・環境変更をユーザー承認なしに強要しない**。GitHub上で画像を開いてユーザーがChatGPTに直接添付する手順を優先。

### 8.4 画像生成時の指示と失敗パターン
- 依頼が**形状ガイド**なら**画像生成を優先しない**。新しい座標・幅/高さ・色面の配置をPython/Pillow等で一意に描き、ガイドPNG＋JSONを制作する。チャットの説明文や油彩の全景絵をガイドにすり替えない。
- 依頼が**完成塗装**ならImageGenに**実際のガイドPNGを第一添付**したうえで、既存採用の`sequel/art/painted_bt_src/stall_food.png`等を画風見本として、`sequel/art/concept/concept_low_dark_a.png`を世界観のみに参照する。**今回は旧屋台`stall_food`の形を模倣しない**。素材単体、正面、画風一致、指定の余白・透過/マゼンタ、文字・余分な建物・看板・人物・地面禁止（人物は内部別レイヤー/配置として必要な場合に限り仕様化）。
- 特に**「仕様の実施結果を報告する画像」**やダッシュボード、Before/After、架空のPythonログ、勝手な成功チェック表は不採用。過去にImageGenがこれを生成したが、**実際にツールが検証を実施したという証拠ではない**。
- **既存の不採用絵を再利用しない**。採用した構造ガイドだけを原本にし、差分を基準原本として連鎖生成しない。
- 生成だけで「形状1px一致」を保証できない。出力画像をPython/Pillowで元ガイドと位置合わせし、各部位の原本マスクで外側を切り落として透明化、サイズ・アルファ・輪郭・halo・ピクセル単位の形状/余白をQAする。ガイドと画像が寸法不一致なら手作業の見た目で合格にしない。
- **ゲーム実装を目的とした画風見本に床・周辺都市を勝手に描き込まない**。豪華なカジノ内部の賑わいは必要だが、通りを歩くキャラと重ねる前景・店の人などのレイヤー設計と混同しない。
- 実機/実Godotが使えなければ`NOT TESTED`で停止。Pythonによる線入りの「縮尺確認画像」は**仕様値を重ねた2D試算**でありGodotレンダリングではない。

### 8.5 新チャットの作業順・受入基準
**最初の成果物は、旧街区と新しいカジノの配置を同じD2カメラから比較できる、座標の確かな検証**。ブランチを分離し、新配置の建物幅・キャバレー・宿・路地の衝突を洗い出す。新配置とスケールが固まったら「フラットカラー形状ガイドPNG＋物理寸法/色凡例JSON」を出し、GitHubの画像埋め込み仕様書でユーザーがChatGPTに実添付できるようにする。次にガイドを編集入力とする完成塗装、マスク・寸法QA、Godotの実スクリーンショット受入の順で進める。

- **PASS**: GitHubの本物PNG添付、スケール/形状の検査数値、実Godotスクリーンショットに対応した根拠を取得した工程のみ。
- **FAIL**: 原本不一致、画像の受け渡し不備、生成が仕様ボードになる、余計な背景や人物、配置衝突。
- **NOT TESTED**: ユーザーがまだ添付していない画像、GitHub上/ブラウザ上でまだ表示確認していない画像、Godot未起動、端末未実測。**判定を推測で補わない**。
