# Web 版の起動と動作の重さ（2026-11-07 計測。直す前の報告）

計測の条件（事実）：パソコンの chromium（playwright、描画は swiftshader＝**CPU でのソフト描画**）、画面 844×390（iPhone 横持ち）。「iPhone 相当」は deviceScaleFactor 3（描画 2532×1170）。手元のサーバーは Pages と同じく gzip で送る（`tools/serve_gzip.py`）。**iPhone の実機ではない**：fps の絶対値は iPhone と大きく違う（ソフト描画は塗る画素の数がほぼそのまま重さになる）。要素ごとの「差」と、サイズ・時間の事実を使う。

計測の仕組み（今回足した。ゲームの動きは変えない）：
- `?perf=1`：1 秒ごとに console へ `PERF`（fps・コマの時間・3D と 2D の draw call・テクスチャのメモリ・2D の層の大きさと絵の数・重なりの目安）、50ms を超えたコマは `PERF_SPIKE`。起動の各段は常に `BOOT <段> <ms>`。
- 切り分け：`?fx2d=0`（2D の層にエフェクトを出さない）、`?fxglow=0`（2D の層の glow を切る）、`?glow3d=0`（3D の glow を切る）、`?vig=0`（画面の仕上げ＝画面を読む層を出さない）。`?fxtest=1` と組み合わせる。

- 2D の層の重なりの目安（絵の面積の合計÷画面）：ふだん 0〜0.5、撃破・大技の瞬間 1.3〜1.7（画面 1.7 枚分）。

## 5. 直した結果（2026-11-07、ユーザー指示の 1〜5）

### 5-1. 2D の層：エフェクトが無い間は止める（採用・実装）
- `fx2d.gd`：絵が 1 つも無くなったら SubViewport を `UPDATE_DISABLED`＋表示を隠す。出すときに `UPDATE_ALWAYS` に戻す。比べる用に `?fxidle=0`（前と同じく毎コマ描く）。
- fps（ブラウザで数えた値、ソフト描画）：

| 場面 | 前（`fxidle=0`） | 後 |
|---|---|---|
| 普段の画面（等倍） | 5.34 | **6.39（+20％）** |
| 普段の画面（×2） | 1.99 | **2.81（+41％）** |
| `?fxtest=1`（1 秒おきにエフェクト、等倍） | 5.60 | 5.96（+6％） |
| `?fxtest=1`（×2） | 1.98 | 2.33（+18％） |

### 5-2. 2D の層を半分の解像度で描く版（**作っただけ。採否はユーザー判定**）
- `?fxhalf=1`（環境変数 `FXHALF=1`）。座標は同じで、層の画素だけ縦横半分。
- fps：`?fxtest=1` で 等倍 5.96→**6.90（+16％）**、×2 2.33→**2.67（+15％）**。エフェクトが無い時は 5-1 で止まっているので差は無い。
- 見た目（同じコマ、`vfxlab`）：`web_perf_img/fxhalf_full_vs_half.webp`（左＝今、右＝半分。上段が等倍の範囲、下段が拡大）。事実：**細い火花が点線のように途切れる**、強い当たりの輪の縁が少しギザギザになる。閃光・三日月・炎の大きな形はほぼ同じ。

### 5-3. 敵の攻撃の絵 4 枚を非可逆で取り込み（採用・実装）
- `foeduel_1_1/1_2/3_1/3_2_p.webp.import`：`compress/mode` 0（可逆）→ **1（非可逆）、品質 0.95**。元がもう非可逆の WebP。
- pck の中：10.5MB → **3.8MB**。本体 index.pck：46.6MB → **39.9MB**。
- 画質（PIL で同じ品質に再圧縮して元と比べた目安）：品質 0.9 だと 39.1〜39.5dB（目安の 40dB を下回る）→ 0.95 にした：46.5〜47.1dB（目では分からない見込み）。GPU のメモリは変わらない（展開すると同じ）。

### 5-4. ラナの絵を Basis Universal で（**試しただけ。まだ採用しない**）
- 作業用の別のプロジェクトで rana2_0・rana2_5 を `compress/mode=4`（Basis Universal）で取り込み、Godot で読んで展開した。パソコンでは BC7（1 画素 1 バイト）に変換された。iPhone では ASTC 4×4 か ETC2（どちらも 1 画素 1 バイト）に変換される（推測、実機未確認）。
- pck の大きさ：rana2_0 3.55MB→**1.65MB**、rana2_5 2.86MB→**1.37MB**（約 47％）。ラナ全体の見込み 32.1MB→**約 15MB**。
- GPU のメモリ：1 画素 4 バイト→1 バイト。ラナ全体 151MB→**約 38MB**。
- 画質：待機のコマで元との差 **PSNR 30.4dB**。`web_perf_img/rana_basis_vs_lossless.png`（左＝元、右＝Basis。全身、顔・剣の刃・髪の縁を 5.3 倍に拡大、画素のまま）。事実：剣の刃の縁にうっすら色のにじみ、肌と金の色がわずかに鈍い、細かい模様の段が少し崩れる。全身の大きさではほぼ同じに見える。
- 注意：ユーザー決定「ラナの絵は可逆（解像度・画質を下げない）」に触れる。採否はユーザー判定。

### 5-5. 回線を絞ると d1 の後 57 秒待つ（**原因を特定。直す前の報告**）
- 時系列（20Mbps・40ms の模擬。`DL` はゲーム側の記録、`要求`・`受信完了` はブラウザ側）：

| 時刻 | 起きたこと |
|---|---|
| 32.8s | ゲームが d1.pck の取得を始める（ブラウザの要求 32.9s） |
| 40.5s | **ブラウザ側では d1.pck を受け取り終えた**（17.5MB を 8 秒＝20Mbps どおり） |
| 34.8〜94.9s | ゲーム側は 2 秒ごとに **0.5〜0.6MB しか読めない**（1 コマ約 4.6KB、ゲームは 60 コマ/秒で回っている） |
| 96.2s | ゲーム側で読み終える（63.4 秒、3799 コマ）。ファイルに書く 0.01 秒、pck の読み込み 0.001 秒 |
| 99.0s | 遊べる |
- 回線を絞らない時：d1 を 1.2 秒・69 コマで読む（1 コマ約 250KB）。
- **原因（事実＋推測）**：書き込み・pck の読み込みは一瞬（事実）。遅いのはゲーム側の読み取り。1 コマあたりの読める量が、回線が細いと小さくなる（事実：4.6KB/コマ）。推測：Godot の Web の HTTPRequest は、ブラウザが受け取ったデータの塊を 1 コマに 1 つずつしか読まず、回線が細いと塊が小さく届くため、「塊の大きさ×コマ数」で頭打ちになる（`download_chunk_size` を 4MB にしても効かない）。ゲームが重く 1 コマが長い時は、塊がたまって大きくなるので速い（al1：1 コマ約 180KB）。
- 直し方の案：
  1. 地区 pck の取得を、ブラウザの fetch で丸ごと受け取ってから（`JavaScriptBridge` で ArrayBuffer→PackedByteArray）書く。見込み：d1 の 63 秒→ブラウザの受信時間（20Mbps で約 8 秒）。**起動 99s→約 44s**。
  2. 1 に加えて、ページを開いた時に全部の pck（d1・fx1・al1）を wasm・本体と同時に取り始める（index.html でブラウザのキャッシュへ）。見込み：起動に要る量（wasm 10.2＋本体 39.8＋d1 17.5＝67.5MB）を 20Mbps で受け取る時間＝**約 27 秒＋起動の処理 3 秒＝約 30 秒**。fx1・al1 もその間に届く。
- 副作用：1 は Web だけの処理が増える（手元では今のまま）。2 は最初に全部を取りに行く（どうせ全部使う。ダンジョンのボス dg1 は除く）。

### 5-6. `?perf=1` の画面の隅の表示（実装）
- 左上（体力の帯の下）に 30px の黄色い文字で：fps、1 コマの時間（平均・最大）、GPU のメモリ（Godot が数える映像のメモリ）、2D の層の状態（ON／OFF、half）。日本語のフォントがまだ無いので英数字。`web_perf_img/perf_overlay.webp`。
- console には今まで通り `PERF`・`PERF_SPIKE`・`BOOT`・`DL`。
