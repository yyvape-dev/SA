# Web 版の起動と動作の重さ（2026-11-07 計測。直す前の報告）

計測の条件（事実）：パソコンの chromium（playwright、描画は swiftshader＝**CPU でのソフト描画**）、画面 844×390（iPhone 横持ち）。「iPhone 相当」は deviceScaleFactor 3（描画 2532×1170）。手元のサーバーは Pages と同じく gzip で送る（`tools/serve_gzip.py`）。**iPhone の実機ではない**：fps の絶対値は iPhone と大きく違う（ソフト描画は塗る画素の数がほぼそのまま重さになる）。要素ごとの「差」と、サイズ・時間の事実を使う。

計測の仕組み（今回足した。ゲームの動きは変えない）：
- `?perf=1`：1 秒ごとに console へ `PERF`（fps・コマの時間・3D と 2D の draw call・テクスチャのメモリ・2D の層の大きさと絵の数・重なりの目安）、50ms を超えたコマは `PERF_SPIKE`。起動の各段は常に `BOOT <段> <ms>`。
- 切り分け：`?fx2d=0`（2D の層にエフェクトを出さない）、`?fxglow=0`（2D の層の glow を切る）、`?glow3d=0`（3D の glow を切る）、`?vig=0`（画面の仕上げ＝画面を読む層を出さない）。`?fxtest=1` と組み合わせる。

|---|---|---|

| main の開始 | 2.09s | 35.5s |
| d1.pck（背景 17.5MB）の受信 | 2.80s | 43.2s |

- 事実（**原因は未特定**）：回線を絞ると、d1.pck の受信がブラウザで終わった（43s）あと、ゲームが使えるようになるまで **57 秒** かかった（手元では 0.4 秒）。推測：Godot の Web の HTTPRequest の読み取りか、受け取った後の書き込み（`user://`＝IndexedDB）。要調査。

## 2. 動作（?fxtest=1、ブラウザで数えた fps、各 2 回）
| 条件 | 等倍（844×390） | ×2（1688×780） |
|---|---|---|
| 全部あり | 6.11・5.52 | 2.07・2.06 |
| `fx2d=0`（エフェクトを出さない） | 6.28・6.38 | 2.05・2.13 |
| **`fxglow=0`（2D の層の glow だけ切る）** | **7.75・7.83** | **2.64・2.58** |
| `glow3d=0`（3D の glow を切る） | 6.36・6.12 | 2.14・2.12 |
| `vig=0`（画面の仕上げを切る） | 5.86・6.27 | 2.21・2.13 |
| `fx2d=0&glow3d=0&vig=0` | 6.31・6.67 | 2.42 |
- ×3（iPhone 相当 2532×1170）：どの条件も約 1fps（ソフト描画では差が埋もれる）。
- **事実：2D の層の glow を切ると fps が約 27％ 上がる（等倍・×2 とも）。エフェクトを出さない（fx2d=0）だけでは上がらない＝エフェクトが無いコマでも、全画面の HDR の層（`SubViewport`、ウィンドウの実寸＝iPhone で 2532×1170、RGBA16F）と glow を毎コマ描いている。**
- 3D の glow・画面の仕上げ：それぞれ数％（測り方の揺れと同じくらい）。
- draw call（1 コマ）：3D 69〜107、2D（UI など）47。描画の CPU の時間 0.5〜1.3ms（CPU 側は重くない）。GPU の時間は、この環境では測れない（WebGL の時間計測が無く 0）。
- 2D の層の重なりの目安（絵の面積の合計÷画面）：ふだん 0〜0.5、撃破・大技の瞬間 1.3〜1.7（画面 1.7 枚分）。
- 初めてエフェクトを出したときの止まり：**この環境では検出できず**（毎コマ約 133ms の中で、エフェクトを出したコマの最大 142〜150ms＝ふだんと同じ揺れ）。iPhone ではシェーダーの準備（Metal への変換）で止まる可能性がある（推測、未計測）。

## 3. 原因と直し方（判断待ち）
| # | 原因（数字） | 直し方 | 効果の見込み | 副作用・注意 |
|---|---|---|---|---|
| 1 | 2D の層の glow が、エフェクトが無いコマでも全画面で毎コマ（fps 約 −27％） | 層に絵が 1 つも無い間は SubViewport を止めて隠す（`UPDATE_DISABLED`）。出ている間だけ描く | 出ていない時 +約 27％ の見込み（ふだんの戦闘の大半）。出ている時は変わらない | ほぼ無い。出始めの 1 コマの遅れが出ないか確認 |
| 1b | 同上（出ている時） | 2D の層の glow を半分の解像度で（層の glow の段数・強さを減らす） | 出ている時の重さを減らす | 「解像度を下げない」の決まりに触れるか、ユーザー判断（絵ではなく光のにじみの計算だけ） |
| 2 | 本体の起動に 74MB を受け取る（20Mbps で約 30 秒＋待ち） | ラナの絵のうち、最初に要らない技の絵（必殺技・技・長押し）を別の pck にして後から読む | 本体の pck が数 MB〜十数 MB 減る（どの絵が要るか要調査） | 技を初めて使う前に読み終えていないと出ない（読み込み待ちの扱いが要る） |
| 3 | 敵の攻撃の絵が可逆で取り込まれ 2.6 倍（10.5MB、元 4.1MB） | 取り込みを非可逆（元と同じ品質 0.9〜0.95）に | 本体 −約 6MB | 非可逆→非可逆でわずかに劣化（元がもう非可逆なので目では分からない見込み）。並べて確かめる |
| 4 | 絵の GPU メモリ 約 500MB（ラナ 151・リリィ 114・敵 75） | VRAM 圧縮（iPhone は ASTC／ETC2） | メモリ 1/4〜1/8 | **画質が落ちる（ユーザー決定「ラナは可逆」に反する）**。パソコン用とスマホ用の 2 形式で pck が倍になる。ユーザー判断 |
| 4b | 同上 | 使わない絵を捨てる（ボスの絵を出口で解放、カットインを使う時だけ読む） | 数十 MB | 読み直しの待ちが出る |
| 5 | pck を順番に取る（本体の後に d1、その後に fx1・al1） | index.html で、wasm と同時に全部の pck を取り始める（ブラウザのキャッシュに入れる） | 回線の待ちが重なり、全体が短くなる | 最初の通信量が増える（どうせ全部使う） |
| 6 | 回線を絞ると d1 を使えるまで 57 秒余分（原因不明） | 原因を調べる（HTTPRequest の読み取り・IndexedDB への書き込みの時間を分けて測る） | 最大で 57 秒短くなる | — |
| 7 | wasm 10.2MB（gzip）。Pages は br を返さない | 使わない機能を外して Godot を自分で組み直す（2D 物理・ナビ・XR など） | 推測：wasm 30〜40％ 減 | 組み直しの手間が大きい。更新のたびに組み直し |
| 8 | `cache-control: max-age=600` | Pages では変えられない。版の番号付きのファイル名にしてキャッシュを長く効かせるには別の配信先が要る | 2 回目以降の起動が速くなる | 配信先を変える手間 |
| 9 | 初めてのエフェクトの止まり（この環境では検出できず） | 読み込みの最後に、画面の外で全部のエフェクトを 1 回ずつ出す（準備運動） | iPhone で最初の当たりのカクつきを防ぐ（未計測） | 起動が少し延びる |
| 10 | 3D の glow・画面の仕上げ（それぞれ数％） | 今は直さない（効果が小さい） | — | — |
